# M2.5 solver bake-off evidence

Recorded: 2026-07-26

This record compares the clean-room constructive backend with the two
exact-version library adapters introduced for the mandatory solver bake-off:

- `bin-packing = 0.3.0`, with default features disabled and only `three-d`;
- `u-nesting-d3 = 0.6.0`, with its default sequential feature set; and
- the in-tree clean-room event-based constructive backend.

No candidate is selected by this record. Selection and rejection decisions are
reserved for the M2.6 ADR.

Historical note: M2.6 subsequently selected the clean-room backend and removed
both external adapters. Candidate-specific reproduction commands require the
M2.5 tree at commit `1f73221`; the accepted decision is
[`../decisions/0001-solver-backend.md`](../decisions/0001-solver-backend.md).

## Correctness and objective quality

All reported solutions pass BoxPacker's independent exact-integer validator.
The known-answer, geometric-adversarial, current, reversed-current, and
generated 8-container/77-item fixtures are asserted in
`tests/bakeoff_fixtures.rs`.

The objective is the provisional D-004 lexicographic order: packed volume,
packed count, fewer used containers, less unsupported area, less occupied
bounding volume, and a deterministic geometry key.

| Backend | Current fixture: placed / packed volume | 8/77: placed / packed volume | 8/77: used / unsupported / bounding |
| --- | ---: | ---: | ---: |
| Clean-room constructive | 53 / 587,815.524 | 73 / 694,614.920 | 8 / 199.220 / 836,936.280 |
| `bin-packing` contact EP | 41 / 535,042.896 | 70 / 687,975.920 | 8 / 362.560 / 807,771.800 |
| `u-nesting-d3` sequential EP | 49 / 568,460.714 | 73 / 694,614.920 | 8 / 282.900 / 830,038.000 |

The saved legacy fixture baseline is 49/57 placed, 582,885.612 packed volume,
and 79.30% total-container utilization. Only the clean-room backend improves
its primary packed-volume result on the current fixture.

Reversing both container and item input arrays preserves the full
`ObjectiveValue` for every candidate. Repeated runs with the same fixed seed
and effort produce byte-for-byte equal domain solutions for every candidate.

## Runtime

Criterion 0.8.2 measured release-mode solve calls, including each adapter's
independent validation, on native ARM64 macOS 26.5.2 with the locked
`rustc 1.97.1` toolchain. Each group used 10 samples, a one-second warm-up, and
a two-second measurement window. Intervals below are Criterion's reported
lower estimate, point estimate, and upper estimate.

| Backend | Current 6/57 | Scale 8/77 |
| --- | ---: | ---: |
| Clean-room constructive | 573.37–577.17–581.27 µs | 844.43–851.11–858.35 µs |
| `bin-packing` contact EP | 42.366–42.831–43.306 ms | 181.03–182.70–184.33 ms |
| `u-nesting-d3` sequential EP | 284.28–286.24–289.21 µs | 438.69–440.12–441.38 µs |

These are development-machine comparisons, not service-level guarantees. The
benchmark can be rerun with:

```sh
devenv shell -- cargo bench --bench current_fixture -- --noplot
```

## Deadline behavior and metrics

- The clean-room backend checks its domain deadline while enumerating
  candidates and returns its valid incumbent.
- `u-nesting-d3` exposes a time limit for its shared solver configuration. Its
  adapter returns an independently valid incumbent within a 5 ms budget plus a
  250 ms shutdown allowance on the 8/77 fixture.
- `bin-packing` 0.3.0 has no deadline or cancellation option on its 3D solve
  API, so BoxPacker cannot enforce a request deadline inside a solve. This is a
  material API gap and the reason it is excluded from the deadline test.
- The clean-room backend and `bin-packing` adapter report explored candidate
  counts. The selected `u-nesting-d3` sequential EP API does not expose a
  compatible explored-state metric, so the adapter cannot supply one.

The deadline and fixed-effort assertions live in
`tests/bakeoff_evaluation.rs`.

## Model fit and integration risk

### Clean-room constructive

- Uses BoxPacker's checked scaled integers directly.
- Handles heterogeneous container inventories in one solve.
- Uses the domain objective, deadline, solution, and metrics types without
  conversion.
- Adds no solver dependency and is already strictly better than the legacy
  saved result.
- It is a deterministic constructive baseline rather than an anytime
  improvement engine; M3 must add bounded improvement neighborhoods.

### `bin-packing` 0.3.0

- Natively accepts heterogeneous multi-bin inventory and deterministic seeds.
- Uses unsigned integer dimensions, but caps each axis at 32,768; the adapter
  must reject otherwise valid BoxPacker instances above that limit.
- Its internal ranking prioritizes unplaced item count, which does not match
  provisional D-004 volume-first ordering.
- The tested contact-point extreme-points strategy is materially slower and
  lower quality on both representative fixtures.
- It has no 3D solve deadline/cancellation API.

### `u-nesting-d3` 0.6.0

- Its tested sequential extreme-point implementation is the fastest candidate.
- The API solves against one boundary at a time, so the adapter must sequence
  heterogeneous containers itself rather than optimize inventory jointly.
- Geometry and placements use `f64`. The adapter sends exactly representable
  scaled integers, accepts only integral returned coordinates, and relies on
  BoxPacker's exact validator; this is still a wider conversion boundary than
  the in-tree backend.
- Its deterministic extreme-point path does not consume BoxPacker's seed, and
  the shared randomized configuration does not expose a seed in this version.
- It ties the clean-room primary result on 8/77 but loses on support, and it
  does not beat the saved legacy result on the current fixture.

## Portability and dependency cost

A native ARM64 macOS release build passed in the locked devenv environment.
Both candidates are Rust libraries with optional parallel features disabled;
no external native solver is enabled. Their enabled production dependency
trees are:

- `bin-packing`: `rand`, `serde`, and `thiserror`, plus their Rust support
  crates;
- `u-nesting-d3`: `u-nesting-core`, `u-geometry`, `u-metaheur`, `u-numflow`,
  `nalgebra`, `rand`, `thiserror`, and their Rust support crates.

The previously recorded x86-64 Linux devenv pass predates these candidate
dependencies, so it does not certify the adapters. Automated locked
dual-platform release verification remains M4.4. This uncertainty is a
candidate-selection risk; it is not hidden by changing the portable devenv
configuration.

Criterion is an exact-version development dependency only and does not enter
the production binary dependency graph.

## Maintenance and licensing snapshot

The snapshot below was inspected on 2026-07-26 from each crate's published
metadata and official repository. Repository popularity is context, not a
quality gate.

| Candidate | License | Published/toolchain notes | Repository snapshot |
| --- | --- | --- | --- |
| `bin-packing` 0.3.0 | MIT | Requires Rust 1.94; exact version builds with BoxPacker's Rust 1.97.1 | [Official repository](https://github.com/doublesharp/bin-packing): 11 commits, 5 stars, 2 forks, CI/fuzz/bench material present |
| `u-nesting-d3` 0.6.0 | MIT | Exact 0.6.0 builds; 0.7.2 was latest during inspection, so the adapter is already behind the current API | [Official repository](https://github.com/iyulab/U-Nesting): 206 commits, 10 stars, 4 forks, CI/changelog/security material present |

Both licenses are compatible with retaining an adapter. Neither project's
maintenance signals overcome the measured objective/model-fit gaps; M2.6 must
weigh those gaps explicitly.
